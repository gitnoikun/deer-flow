# DeerFlow 部署指引（代理版）

> 本指引假设：已在服务器配好「走 Windows Clash 代理(192.168.77.10:7897)」，且**由你本人在服务器上执行部署命令**。
> 我已提前完成并验证：配置文件齐备、Docker 代理、全局代理、DeepSeek 模型配置、端口空闲。

---

## 0. 前置：一次性的脚本权限修复

`deploy.sh` 通过 git 同步可能丢了可执行位，只需执行一次：

```bash
cd /opt/code/deer-flow
chmod +x deploy-cn/deploy.sh
```

---

## 1. 启动部署

有两种方式，**推荐 `make` 或直接跑 deploy.sh**。

### 方式 A：直接跑 deploy.sh（推荐，可控）

```bash
cd /opt/code/deer-flow
# 构建镜像（首次较久，约 5-15 分钟）
bash deploy-cn/deploy.sh build

# 启动所有服务（等待健康检查通过）
bash deploy-cn/deploy.sh start
```

### 方式 B：用根 Makefile

```bash
cd /opt/code/deer-flow
make up        # 生产模式启动（Docker stack）
# 或
make dev       # 开发模式（热重载，本地调试）
```

> 二选一即可，别混用。日志路径一致，见下文。

## 2. 部署完成后访问

- **浏览器地址**：`http://<服务器IP>:2026` （你用 `BIND_HOST=0.0.0.0`，跨机可访问）
- **首次访问必须创建 admin 账号**（DeerFlow 强制要求，否则功能受限）

## 3. 出错了该看哪里（重点）

**所有命令的日志都集中在服务器，按需查看：**

| 场景 | 命令 |
| --- | --- |
| **构建失败**（build 阶段） | `bash deploy-cn/deploy.sh build` 的终端输出最直接<br>或到 `/opt/code/deer-flow` 再跑一次看完整报错 |
| **启动/运行失败** | `docker compose -f docker/docker-compose.yaml -p deer-flow logs` |
| **只看 gateway(后端)** 日志 | `docker logs deer-flow-gateway --tail 200` |
| **只看前端** 日志 | `docker logs deer-flow-frontend --tail 100` |
| **服务状态** | `docker compose -f docker/docker-compose.yaml -p deer-flow ps` |
| **健康检查** | `curl -s http://127.0.0.1:8001/health` |
| **重启单个服务** | `docker restart deer-flow-gateway` |
| **停止并清理** | `bash deploy-cn/deploy.sh down` 或 `make stop` |

> 若用了 `make up`，也可直接 `docker compose ps` / `docker compose logs -f`。

## 4. 常见构建/网络报错对照

| 报错特征 | 原因 | 处理 |
| --- | --- | --- |
| `connection timed out` / `Failed to fetch` (pypi/npm) | 构建期容器没走代理 | 确认 Clash `allow-lan` 开着；确认 `/etc/environment` 有代理（应已配）；重试 |
| `pull access denied` / `manifest unknown` (ghcr) | 代理没覆盖到拉取 | 已配 daemon 代理，重试；若仍失败在 `.env` 加 `NO_PROXY` 排除, 并确认代理含 ghcr |
| `ERROR: failed to solve: process ... did not complete successfully` | 构建中某步(如 uv/npm)失败 | 看该步上层日志具体包名；通常是代理/镜像源抖动，**直接重跑 build** |
| `naming to ... deer-flow-gateway` 缺失 | gateway 镜像没建出来 | 重跑 `deploy.sh build`；前端/其他服务已缓存会跳过 |
| `dexec: ... port already in use` / `Bind for ... failed` | 端口被占 | `ss -tlnp \| grep 2026` 找占用进程；改 `.env` 的 `PORT` 或停掉占用者 |
| 容器反复重启 / `healthcheck` 失败 | 后端启动抛错/配置错 | `docker logs deer-flow-gateway --tail 300` 看 traceback；常见是 `config.yaml` 模型/base_url 或 API key 问题 |

## 5. 构建失败要不要清缓存（你问的）

通常**不需要**。Docker 有层缓存，重跑 `build` 会自动复用已成功的层（前端/其他服务直接跳过），重试成本低。

只有以下情况才需要清理（会丢缓存，重跑会更久）：

```bash
# 只清构建缓存（不动镜像和容器数据）
docker builder prune -af

# 全清（含镜像、容器、网络、构建缓存）——谨慎，会清掉所有东西
docker system prune -af --volumes
```

建议：**先直接重跑 `build` 看是否秒过**。只有反复在同一层失败（如 uv sync 反复卡）才 `docker builder prune -af` 后重跑。

## 6. 关键配置文件（已就绪，勿动内容）

- `/opt/code/deer-flow/.env`               — 代理 + DeepSeek Key + 端口
- `/opt/code/deer-flow/config.yaml`        — DeepSeek 模型 + 本地沙箱
- `/opt/code/deer-flow/extensions_config.json` — MCP/技能（空，可后加）
- `/opt/code/deer-flow/frontend/.env`      — 前端 SSR 变量

> 若启动报「模型认证失败」，优先检查 `config.yaml` 里 `base_url`（应为 `https://api.deepseek.com/v1`）和 `.env` 的 `DEEPSEEK_API_KEY`。
